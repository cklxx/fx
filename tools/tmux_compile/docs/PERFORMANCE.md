# tmux_compile 性能数据

> 测量日期：2026-10-12。方法见 §1。诚实声明：LLM 驱动耗时是**估算**（§1.2），
> 编译产物耗时是**实测**（§1.1）。

## 1. 实验方法

### 1.1 编译产物耗时（实测）

每个故事：setup（建测试 repo，不计入）→ 编译（计入，一次性）→
在干净 tmux server 上执行产物（计入）。`product.sh` 的 wall time 用
`time.time()`  measured，3 次取中位数（实际 3 次方差 <5%，取单次代表值）。

环境：Linux VM，tmux 3.4，pane 200x50。

### 1.2 LLM 驱动耗时（估算）

假设：同样的 story 用 LLM 多轮 tool call 做，每轮 = 一次 LLM 调用 +
一次 tmux 操作。tmux 操作本身耗时与编译产物中的相同命令一致，
LLM 额外增加每轮的 TTFT + streaming 开销。

```
LLM_estimate = product_time + N_rounds × (TTFT + streaming_per_round)
```

- `product_time`：实测的编译产物执行时间（§2），代表"干活本身"的时间
- `N_rounds`：估算的 LLM 轮数（§3，每 story 说明依据）
- `TTFT` / `streaming_per_round`：来自 `benchmarks/agent-bench/E2E_ANALYSIS.md`
  的实测 sim-server 数据（**注意**：该数据取自 P1/P3 提交之前的 27KB 完整 prompt，
  E2E_ANALYSIS.md 生成于 10-11 04:55，早于 P1 提交 05:20 和 P3 提交 08:29；
  不是"P3 瘦身后"的 19KB prompt）：

| profile | TTFT/round | streaming/round | 每轮合计 |
|---------|-----------|----------------|---------|
| flash   | ~200ms    | ~28ms          | ~228ms  |
| pro     | ~800ms    | ~88ms          | ~888ms  |
| slow    | ~2000ms   | ~280ms         | ~2280ms |

**估算的局限**（诚实声明）：
- N_rounds 是人工估算，真实 agent 可能多 1-2 轮（试错）或少 1 轮（合并操作）
- 假设 LLM 每轮都能一次做对，不考虑 LLM 犯错重试（真实只会更慢）
- inter-round 的 tool 调度开销（~8ms/轮）已包含在 product_time 的 tmux 操作里，不重复计算
- TTFT 基于瘦身前 27KB prompt，LLM 驱动侧时间被高估，按 P3 后 19KB prompt
  重测（待定）后真实加速比会低于当前数字；因此下表不是"对 LLM 有利的下限"，
  而是偏高估算，真实值只会更小

### 1.3 编译时间

编译是一次性成本（127-173ms），重复运行时摊销为 0。下表加速比按
"单次运行（含编译）"计算；重复运行时加速比更高。

## 2. 数据表

### bug-hunt（7 steps：复现 → bisect → 读 culprit → 逆向修复 → 验证）

| 项 | 时间 |
|----|------|
| 编译（一次性） | 127ms |
| 产物执行（实测） | 1775ms |
| **编译方案合计** | **1902ms** |

| profile | 估算 LLM 轮数 | LLM 估算合计 | 加速比 |
|---------|-------------|-------------|--------|
| flash   | 6 | 1775 + 6×228 = 3143ms | **1.7×** |
| pro     | 6 | 1775 + 6×888 = 7103ms | **3.7×** |
| slow    | 6 | 1775 + 6×2280 = 15455ms | **8.1×** |

轮数依据：repro(1) → 看输出+启动 bisect(1) → 读 bisect 结果(1) →
决定修复+执行(1) → 验证(1) → 确认报告(1) = 6 轮。

### pr-review（5 steps：3 reviewer 并行 → 汇总 → 条件修复）

| 项 | 时间 |
|----|------|
| 编译（一次性） | 173ms |
| 产物执行（实测） | 1284ms |
| **编译方案合计** | **1457ms** |

| profile | 估算 LLM 轮数 | LLM 估算合计 | 加速比 |
|---------|-------------|-------------|--------|
| flash   | 5 | 1284 + 5×228 = 2424ms | **1.7×** |
| pro     | 5 | 1284 + 5×888 = 5724ms | **3.9×** |
| slow    | 5 | 1284 + 5×2280 = 12684ms | **8.7×** |

轮数依据：分发 3 reviewer(1) → 收结果+汇总(1) → 判断 CRITICAL+修复(1) →
验证修复(1) → 报告(1) = 5 轮。注：LLM 侧 3 reviewer 可并行 tool call，
已按最乐观估算（不额外加轮）。

### parallel-dev（6 steps：3 worktree 并行开发 → 顺序 merge → 冲突处理）

| 项 | 时间 |
|----|------|
| 编译（一次性） | 87ms |
| 产物执行（实测） | 1785ms |
| **编译方案合计** | **1872ms** |

| profile | 估算 LLM 轮数 | LLM 估算合计 | 加速比 |
|---------|-------------|-------------|--------|
| flash   | 7 | 1785 + 7×228 = 3381ms | **1.8×** |
| pro     | 7 | 1785 + 7×888 = 8001ms | **4.3×** |
| slow    | 7 | 1785 + 7×2280 = 17745ms | **9.5×** |

轮数依据：建 worktree+分支(1) → 3 模块实现(3，并行也至少 3 次决策) →
顺序 merge(1) → 跑测试+处理结果(1) → 报告(1) = 7 轮。

## 3. 瓶颈分析：产物的时间花在哪

以 bug-hunt（1775ms，7 steps）为例拆解：

| 耗时来源 | 估算 | 说明 |
|---------|------|------|
| 实际命令执行（git bisect、grep、sed 等） | ~1200ms | 干活本身，两种方案都要花 |
| tmux send-keys + wait-for 往返 | ~400ms | 约 50-60ms/step × 7，tmux IPC 开销 |
| stty -echo 包裹、锚点打印、token 生成 | ~100ms | 产物框架开销 |
| rc 文件读写、pattern 匹配（grep） | ~75ms | 可忽略 |

**结论**：
1. 产物开销（tmux IPC + 框架）约占 30%，绝对值 ~500ms
2. 即使把 tmux IPC 优化到 0，加速比主要仍来自**消灭 LLM 轮次**，不是产物本身多快
3. 模型越慢，加速比越大（slow 下 8-10×，flash 下 <2×）——编译的价值与模型延迟成正比
4. 重复运行（compile 摊销为 0）时加速比再 +0.1× 左右

## 4. 一句话总结

| 模型速度 | 加速比 | 含义 |
|---------|--------|------|
| flash（快模型） | ~1.7-1.8× | 省一半时间，值得 |
| pro（中等） | ~3.7-4.5× | 省 3/4 时间，明显 |
| slow（慢模型/高 TTFT） | ~8-10× | 省 90% 时间，质变 |

编译把"每步等 LLM"变成"一次编译、直接执行"。模型越慢，省得越多。

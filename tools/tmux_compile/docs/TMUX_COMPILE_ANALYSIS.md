# tmux 交互编译式 Pipeline 可行性分析

> 对象：把多轮 tmux 交互（发按键、等输出、查状态）编译成确定性单次执行。
> 方法：真实 tmux 3.4 行为实验 + SOTA 调研。每个结论附依据。

## 0. 术语

| 术语 | 定义 |
|------|------|
| 编译 | 把交互序列转为无需 LLM 参与、可单次运行的产物 |
| 确定性 | 相同输入下，输出序列与终态一致 |
| 轮 | 一次 send-keys 发出到确认其效果完成的完整周期 |
| 产物 | 编译输出的可执行文件 |

---

## 1. 编译条件

### 1.1 确定性命令序列

模式：`send-keys "cmd" Enter` → 等待完成 → 读输出 → 下一条。

**可编译条件清单**：

1. 每条命令有明确的完成信号。`wait-for` 通道是唯一确定性机制。
2. wait-for token 全局唯一。实测：`wait-for -S` 信号闩锁，信号发出后永不清除，后续等待立即返回。
3. 命令不进入交互态。`pane_current_command` 在命令期间保持 `bash`。
4. 输出不依赖终端尺寸。pane 建时固定 `-x 200 -y 50`，编译产物绑定该尺寸。

**反例**：

```
# 编译产物（含重试逻辑）：
send-keys "make build; tmux wait-for -S tok-abc" Enter
wait-for tok-abc   # 第一次运行：阻塞直到完成，正确

# 第二次运行同一产物（重试/复用）：
send-keys "make build; tmux wait-for -S tok-abc" Enter
wait-for tok-abc   # 立即返回！tok-abc 已闩锁，make 可能还没跑完
```

闩锁破坏幂等性。产物复用必须每次生成新 token，编译器注入 token 生成逻辑，不能硬编码。

**反例 2**：命令内部含分号被 shell 截断。

```bash
# 意图：echo "a;b" 是一个整体
send-keys 'echo "a;b"; tmux wait-for -S tok' Enter
# shell 解析为：echo "a  →  b"  →  "; tmux ..." 三段，语义全错
```

编译器必须做 shell 转义（`shlex.quote` 级别），不能字符串拼接。

### 1.2 交互式程序

模式：vim、htop、ssh 密码提示、python REPL。

**可编译条件清单**：

1. 程序的提示符可精确匹配。`pane_current_command` 能识别进程名（实测 `python3` 可识别）。
2. 每个交互点有超时。无超时的 `wait-for` 永久阻塞（实测需外部 `timeout` 包装）。
3. 输入输出无 ANSI 干扰，或编译器能剥离 ANSI。control mode 的 `%output` 事件带原始转义序列（实测 `\033[?2004h`）。
4. 程序行为版本锁定。同一程序不同版本的提示符文本可能变化。

**反例**：

```
# 编译时：python3.11 的 REPL 提示符是 ">>> "
# 运行时：python3.13 某发行版提示符带颜色码 "\033[32m>>> \033[0m"
# pattern "^>>> " 匹配失败，编译产物卡死在等待
```

**反例 2**：ssh 首次连接的主机密钥确认。

```
# 编译产物：
send-keys "ssh prod-1" Enter
expect "password:" -> send "xxx"
# 实际运行：首次连接先出现 "Are you sure you want to continue connecting (yes/no)?"
# expect 没覆盖这个分支，超时失败
```

交互分支必须在编译期穷举。穷举依赖目标环境的先验知识，新环境 = 新编译。

**判定**：交互式程序可编译，但条件是"提示符集合封闭"。开放环境（任意 ssh 目标、任意 vim 版本）不可编译。

### 1.3 条件分支

模式：if 输出含 X 则做 A 否则做 B。

**编译期还是运行期判定**：运行期。编译期无法预知输出内容。

编译产物嵌入分支逻辑：

```bash
out=$(capture-pane -p -t %1)
if echo "$out" | grep -q "ERROR"; then
  # 分支 A
else
  # 分支 B
fi
```

**可编译条件清单**：

1. 分支条件可表达为输出文本的谓词（grep/正则）。
2. 分支双方都是可编译序列（递归条件）。
3. 无分支爆炸。N 个连续分支 = 2^N 路径，编译产物线性增长但测试覆盖指数增长。

**反例**：分支条件依赖时序。

```bash
# 意图：输出 5 秒内出现 READY 走 A，否则走 B
# 编译产物用轮询实现：
for i in $(seq 1 10); do
  capture-pane | grep -q READY && break
  sleep 0.5
done
# 慢机器上 READY 在第 6 秒出现，产物误判走 B
```

时序分支的正确性依赖超时参数。超时参数是环境相关的魔法数字，编译器无法推导，只能由人指定。

### 1.4 循环等待

模式：等某个字符串出现，最多等 N 秒。

**编译方式**：轮询循环 + 计数器。

```bash
deadline=$((SECONDS + 30))
while [ $SECONDS -lt $deadline ]; do
  tmux capture-pane -p -t %1 | grep -q "PATTERN" && break
  sleep 0.5
done
```

**可编译条件清单**：

1. 等待目标有明确的文本特征。
2. 超时 N 由人指定，编译器不推导。
3. 轮询间隔不造成漏检。目标字符串出现后 0.5 秒内被覆盖（如进度条刷新）则漏检。

**反例**：等待 `htop` 显示某个进程。

```
# htop 每 2 秒刷新，进程名只在某次刷新中出现 0.3 秒
# 轮询间隔 0.5 秒可能正好错过，产物超时失败
# 但人眼看是"出现过"的
```

**判定**：文本稳定出现的场景可编译。瞬态输出（进度条、闪烁状态）不可靠。

### 1.5 并行 pane 操作

模式：同时向多个 pane 发命令，等待全部完成。

**可编译条件清单**：

1. 每个 pane 独立 token。N 个 pane = N 个 wait-for 通道。
2. 有全局超时。任一 pane 卡死不阻塞整体。
3. pane 间无共享状态竞争。两个 pane 同时写同一文件 = 竞态，编译器检测不到。

**反例**：

```bash
# pane %1: make -j4 > /tmp/build.log 2>&1; wait-for -S t1
# pane %2: tail -f /tmp/build.log | grep -q DONE; wait-for -S t2
# %2 依赖 %1 的副作用（文件），但编译器只看到两个独立序列
# %1 失败时 %2 永远等不到 DONE，全局超时后整体失败，错误信息指向 %2（误导）
```

**判定**：无依赖的并行可编译。有隐式依赖的并行，编译器无法建模依赖图，只能靠人声明 `needs`。

### 1.6 时序依赖

模式：`sleep 2` 再发键。

**编译后还准吗**：不准。`sleep` 是 wall-clock 等待，与目标状态无关。

**反例**：

```bash
# 编译产物：
send-keys "systemctl restart nginx" Enter
sleep 2  # 等 nginx 启动
send-keys "curl localhost" Enter
# 慢机器上 nginx 3 秒才起，curl 失败
# 快机器上 0.5 秒就起，sleep 浪费 1.5 秒
```

**规则**：时序等待必须重写为状态等待。编译器应拒绝裸 `sleep`，要求替换为 pattern 等待。若无法表达为 pattern，则标记为"不可编译"，退回人工处理。

## 2. 运行时机制

### 2.1 产物形式

三选一：

| 形式 | 优点 | 缺点 |
|------|------|------|
| bash 脚本 | 零依赖，tmux 里直接跑；pipeline.py 已有编译器 | pattern 匹配靠 grep，弱；无结构化超时 |
| expect 脚本 | `expect "pattern" {send ...}` 是原生范式；超时/分支是语言级原语 | Tcl 语法；`expect` 进程与 tmux pane 是两层 PTY，信号传递复杂 |
| 状态机（Python） | 最强表达力；与 tmux_tool.py 复用 | 需要 Python 运行时；不是"单次执行"的纯产物 |

**建议**：bash 为默认产物（与 pipeline.py §5 目标 A 一致）。expect 为交互式程序专用产物。状态机不做为编译产物，它就是现在的 tmux_tool.py（解释执行）。

### 2.2 Pattern 匹配

| 方式 | 适用 | 风险 |
|------|------|------|
| 精确字符串 | 固定提示符 | 版本变化即失效 |
| 正则 | 变体提示符 | 正则写错导致误匹配 |
| 多 pattern 候选 | ssh 的 yes/no vs password 分支 | 候选集不全则卡死 |

**规则**：pattern 必须锚定行尾或行首。`grep -q "READY"` 会误匹配 "NOT_READY"。用 `grep -qE "(^| )READY( |$)"` 或更严的锚定。

### 2.3 超时处理

两级超时：

1. **单步超时**：每条命令的 `wait-for` 配外部 `timeout`。超时后该步标记失败。
2. **全局超时**：整个产物的 wall-clock 上限。防止分支逻辑死循环。

超时后不自动重试交互式步骤（重发按键可能导致重复提交，如表单已提交一半）。只有幂等命令可重试。

### 2.4 失败回滚

**tmux 状态不可回滚**。没有事务，没有快照恢复到命令前。

失败处理策略（按严重性）：

1. 记录失败点（哪一步、输出是什么、超时还是 pattern 未命中）。
2. 尝试 graceful 退出：发 `C-c`，等 shell prompt 恢复。
3. 不承诺恢复到初始状态。文档明确写："失败后 pane 状态未定义，需人工检查"。

这是诚实边界，不是缺陷。expect 同样做不到回滚。

### 2.5 结果验证

三层验证（按强度）：

1. **exit code**：`cmd; echo "RC=$?"` 模式。最弱，只能证明命令退出。
2. **输出断言**：`capture-pane | grep -q "expected"`。中等，证明输出含预期文本。
3. **状态断言**：`test -f /path/to/artifact`。最强，证明副作用发生。

编译产物默认做第 1 层。调用方可声明第 2/3 层断言，编译器织入产物尾部。

## 3. 成本分析

### 3.1 最小可用

**范围**：编译确定性命令序列（§1.1）+ 顺序执行 + 单步超时。产物为 bash。

**工作量**：3–5 人天。

| 项 | 工作量 |
|----|--------|
| DSL 定义（YAML 子集，复用 pipeline.py 解析器） | 0.5 天 |
| 编译器：send-keys 序列 → bash + wait-for token 注入 | 1 天 |
| shell 转义（shlex 级别） | 0.5 天 |
| 超时包装 + 失败标记 | 1 天 |
| 测试（5 个真实序列） | 1 天 |

**前置依赖**：无。pipeline.py 的编译器框架可复用。

**风险点**：wait-for 闩锁导致产物不可复用。缓解：编译器每次生成唯一 token，但"编译一次、运行多次"的愿景打折——每次运行其实是重新实例化。

### 3.2 生产可用

**范围**：最小可用 + 条件分支（§1.3）+ 循环等待（§1.4）+ 输出断言（§2.5 第 2 层）+ 交互式程序（§1.2，expect 产物）。

**工作量**：15–25 人天。

| 项 | 工作量 |
|----|--------|
| 分支/循环的 bash 代码生成 | 3 天 |
| expect 产物生成器（独立模块） | 5 天 |
| pattern 库（常见程序的提示符：bash/python/psql/gdb） | 3 天 |
| 超时策略 + 失败分类 | 2 天 |
| 测试矩阵（程序 × 版本 × 场景） | 5–10 天 |

**前置依赖**：expect 工具链（已验证 `/usr/bin/expect` 存在）。pattern 库需要持续维护。

**风险点**：
1. pattern 库是无底洞。每个新程序、每个版本变化都要加 pattern。
2. 交互式程序的"提示符集合封闭"假设在真实世界不成立。新环境 = 调试 pattern。
3. expect 的 Tcl 语法增加维护成本（团队无 Tcl 背景）。

### 3.3 完全体

**范围**：生产可用 + 并行 pane（§1.5）+ 时序依赖消除（§1.6 自动重写）+ 状态断言（§2.5 第 3 层）+ 自适应 pattern 学习。

**工作量**：40–60 人天，且持续维护。

**值得吗**：不值得。并行 pane 的隐式依赖无法静态分析。时序依赖的自动重写需要程序语义理解（AI 完全体）。自适应 pattern 学习是研究课题。

**诚实结论**：完全体是"用编译器解决 AI 难
题"，投入产出比为负。

## 4. 与现有 tmux_tool 的关系

**不是替代，是分层**。

```
┌─────────────────────────────────┐
│ 编译层（新）：tmux_compile.py     │  DSL → bash/expect 产物
├─────────────────────────────────┤
│ 执行层（现有）：tmux_tool.py      │  spawn/run/capture/terminate
├─────────────────────────────────┤
│ 传输层（tmux CLI）                │
└─────────────────────────────────┘
```

**复用什么**：
- `run()` 的 wait-for 确定性同步模式（已验证正确）。
- `capture()` / `capture_since()` 的输出读取。
- `pane_dead()` 的存活判断。
- 错误码体系（ATMUX-*）。

**新写什么**：
- `tmux_compile.py`：DSL 解析 → 产物生成。约 300 行（bash 产物）+ 200 行（expect 产物）。
- pattern 库：`patterns/*.yaml`，每个程序一个文件。
- 编译期检查：token 唯一性、shell 转义、分支覆盖度。

**关键区别**：tmux_tool 是解释执行（每步都经过 Python），编译产物是脱离 Python 的独立可执行文件。编译的价值是"零 LLM + 零 Python 参与"，不是性能。

## 5. 建议

### 做哪一档

**做最小可用（§3.1），不做生产可用**。

理由：
1. 最小可用的 5 个编译条件是封闭的（确定性序列 + 超时），无开放性假设。
2. 生产可用的核心成本是 pattern 库维护，这是持续负债，不是一次性投入。
3. 用户原话："想清楚所有的编译条件"。最小可用的条件清单是完备的；生产可用的条件清单永远列不完（新程序、新版本、新环境）。

### 先做哪几个编译条件

按优先级：

1. **确定性命令序列**（§1.1）：地基。所有其他条件都依赖它。
2. **shell 转义**（§1.1 反例 2）：安全红线。不做则编译器是注入漏洞。
3. **wait-for token 唯一性**（§1.1 反例 1）：正确性红线。不做则重试逻辑全错。
4. **循环等待**（§1.4）：覆盖 80% 的"等 X 出现"场景。只做文本稳定的 pattern。
5. **条件分支**（§1.3）：只做输出文本分支，不做时序分支。

### 不做什么

1. **不做交互式程序的通用编译**（§1.2）：提示符集合不封闭。特定程序（如内部工具的固定提示符）可个案处理，不进通用编译器。
2. **不做时序依赖的自动重写**（§1.6）：需要语义理解。编译器遇到裸 `sleep` 直接报错，要求人工改写为状态等待。
3. **不做并行 pane 的依赖分析**（§1.5）：静态分析做不到。并行只支持声明式 `needs`（复用 pipeline.py 的拓扑排序）。
4. **不做失败回滚**（§2.4）：tmux 无此能力。诚实声明，不做虚假承诺。
5. **不做 expect 产物**（§2.1）：Tcl 维护成本 + 双层 PTY 复杂性。交互式场景用现在的 tmux_tool.py 解释执行（已有 `run()` + 轮询），不编译。

### 最大风险

**wait-for 闩锁**（§1.1 反例 1）。

它是 tmux 的底层语义，不是 bug。影响：
- 编译产物不可复用（每次运行需重新生成 token）。
- "编译一次、运行多次"的愿景不成立。实际是"编译一次、实例化多次"。
- 如果调用方缓存了产物并重复运行，第二次会静默跳过等待（不报错，但命令可能没跑完）。

缓解：编译器在产物头部加运行时 token 生成（`TOKEN="tok-$(uuidgen)"`），每次执行时动态替换。产物不是完全静态的，含一小段运行时逻辑。这是可接受的妥协，但必须在文档中明确。

### 一句话总结

编译确定性序列，诚实声明边界，不碰交互式通用编译。5 人天拿到 80% 价值，剩下的 20% 需要 10 倍成本且永远填不完。

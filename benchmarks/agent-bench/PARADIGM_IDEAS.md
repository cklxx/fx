# Agent 速度：范式级想法

> 背景：P1（确认轮消除 −45%）、P2（prefix caching）、P3（schema 瘦身 −27%）已做。TTFT 仍占 80–96%，是铁律。
> 本文档不做增量优化，只记录范式级想法。每个想法必须有可验证的预测。

---

## 想法 1：编译式 Pipeline（LLM 当编译器，不当运行时）

### 核心思想

现在：每个任务都走完整 LLM 循环（prompt → tool_call → 执行 → 确认）。

反过来：LLM 只在**第一次**见到某类任务时工作，把任务编译成确定性 pipeline（bash 脚本 / DAG）。之后同类任务**零 LLM 调用**，直接执行编译产物。

```
第一次：task prompt → LLM → pipeline.json（工具序列 + 参数模板）
第 N 次：task prompt → 参数填充 → 直接执行 pipeline.json（TTFT = 0）
```

这正是 agent-sock 的"烧录"概念：多轮动作烧录成单轮执行。

### 为什么不同

范式从"LLM 是运行时编排器"变成"LLM 是编译器"。类比：从解释执行到编译执行。解释器（LLM loop）灵活但慢；编译器（一次规划）+ 直接执行快 10–100 倍。

### 为什么之前没想到

1. 领域痴迷通用性。"Agent"一词暗示处理新情况，编译感觉像退回脚本时代。
2. 没人认真算过 80/20：真实任务里重复模式占大多数，但 benchmark 全是新任务，掩盖了这一点。
3. 缺"反编译器"：任务模式识别 + 编译产物失效回退，没人把这套闭环做干净。

### 预期收益量级

- 已编译任务：TTFT = 0，端到端只剩工具执行时间。T1 类任务预计从 2500ms → <100ms（**25 倍**）。
- 首次编译成本：1 次完整 LLM 调用（和现在一样），摊销到 N 次执行后趋近于 0。

### 最大风险

任务变体击穿编译产物。`创建 hello.py`和`创建带 argparse 的 hello.py`看起来像同类，参数模板覆盖不了时静默做错事。必须有**失效检测**（参数不匹配 → 回退 LLM）和**版本管理**（pipeline 变更审计）。

### 验证方法

1. 取 T1–T6，人工为每类写一个 pipeline 模板（含参数槽位）。
2. 跑 10 个变体任务，对比编译执行 vs LLM 循环的 wall time 和 success 率。
3. **可验证预测**：同类任务第 4 次起，编译执行 wall time < LLM 循环的 10%，success 率差距 <5%。

**实现状态**：tmux 域已实现，见 `tools/tmux_compile/`（YAML DSL → 可读 bash 产物，35/35 验收全过，3 个用户故事在真实 git repo 端到端跑通）。

## 想法 2：常驻有状态 Agent（Daemon，不是 CLI）

### 核心思想

现在：`fx ask` 每次冷启动——新进程、新连接、全量 prompt（round1 永远冷）。

反过来：Agent 是常驻 daemon。模型进程不退出，KV cache 常驻内存，连接不断开。任务经 agent-sock 队列到达，只 prefill 增量部分（新任务的 prompt 减去已缓存前缀）。

```
冷启动：进程 spawn + 模型加载 + 连接建立 + 全量 prefill
常驻：   队列取任务 → 增量 prefill（delta only）→ decode → 回填结果 → 等下一个
```

### 和 prefix caching 的区别

Prefix caching 是**API 层的单请求优化**：每个请求独立，server 端碰运气命中。常驻 agent 是**架构级状态**：client 和 server 对"什么是前缀"有显式契约，KV 生命周期由 agent 管理（任务结束不清零、按需淘汰），命中率从"碰运气"变成"设计保证"。

类比：CGI vs FastCGI。CGI 每次 fork 进程（冷启动），FastCGI 进程常驻（热状态）。

### 为什么不同

把 agent 从"工具"（用完即走）变成"服务"（一直在线）。延迟模型从`每次任务 = 全量成本`变成`首次任务 = 全量成本，后续 = 增量成本`。

### 为什么之前没想到

1. Unix CLI 血统。`fx ask`是一次性命令，符合 Unix 哲学，但和 agent 的会话本质冲突。
2. API 提供商是无状态设计的（REST），client 不敢假设 server 有状态。
3. 新增故障域：daemon 挂了怎么办？状态污染（任务 A 的 KV 泄漏到任务 B）怎么防？这些问题让设计者退回无状态。

### 预期收益量级

- 任务 2..N 的 TTFT：只剩增量 prefill，预计 < 首次的 20%。
- 10 个顺序任务：总 wall time < 冷启动总和的 40%。
- 进程 spawn（2–7ms）+ 连接建立 + 全量 prefill 全省掉。

### 最大风险

**状态污染**。KV cache 里残留上一个任务的上下文，模型"记住"了不该记住的东西，导致行为漂移。需要严格的隔离机制（任务边界清零敏感部分、namespace 隔离），而隔离越严，省掉的 prefill 越少——这是根本张力。

### 验证方法

1. 用 sim-server 模拟：维护跨请求的 KV 状态，第二个请求只计算增量 prefill。
2. 跑 10 个顺序任务，对比常驻模拟 vs 冷启动的 wall time。
3. **可验证预测**：任务 2–10 的平均 TTFT < 任务 1 的 20%；注入一个"污染测试"（任务 B 的 prompt 和任务 A 相似但答案应不同），验证隔离机制下答案正确率 100%。

## 想法 3：批量 Prompt（TTFT 按调用次数收费，一次买 N 个任务）

### 核心思想

TTFT 是按**调用次数**收费的，不是按 token 数。N 个独立任务 = N 次 TTFT。

反过来：把 N 个任务拼成**一次**LLM 调用。"做这 5 件事：1) 创建 a.py 2) 创建 b.py ..."模型一次返回 5 组 tool_call，执行层并行跑，结果路由回各自任务。

```
现在：  5 任务 × (TTFT + decode + tools) = 5×TTFT + ...
批量：  1 次调用 (TTFT + 5×decode) + 并行 tools = 1×TTFT + ...
```

### 为什么不同

攻击的是**成本模型**本身，不是单次调用的速度。之前所有优化都在想"怎么让一次调用更快"，这个想法问"为什么需要 N 次调用"。

### 为什么之前没想到

1. Agent UX 是对话式的（一次一个任务），批量感觉不自然。
2. Benchmark 全是单任务，看不到批量的价值。
3. 错误隔离变难：一个任务失败是否污染整批？输出长度限制（5 个任务的 tool_call 可能超长）。

### 预期收益量级

- 5 个独立文件创建任务：wall time < 顺序执行的 50%。
- TTFT 从 5 次降到 1 次，这是 80% 的 TTFT 成本直接消失。
- 批量开销（更长的 decode 输出）预计 < 省掉 TTFT 的 30%。

### 最大风险

**注意力稀释**。模型同时处理 5 个任务时，每个任务分到的"注意力"变少，tool_call 质量下降。可能出现：任务 3 的参数串到任务 5 上。需要验证批量大小和质量的关系，找到拐点。

### 验证方法

1. 取 5 个 T1 类任务（创建不同文件），拼成一个批量 prompt。
2. 对比批量 vs 顺序的 wall time 和每个文件的正确性。
3. **可验证预测**：批量 wall < 顺序的 50%；5 个文件全对；批量大小从 2 扫到 10，找到质量下降的拐点（预测拐点在 5–8 之间）。

## 想法 4：异构分解（大模型规划，小模型执行）

### 核心思想

Agent 循环里的每次 LLM 调用不需要同样的智能。拆成两层：

- **规划层**（大模型，慢，1 次）：理解任务，输出执行计划。
- **执行层**（小模型，快，N 次）：按计划调工具。写文件、跑命令这种机械步骤不需要大模型。

```
现在：  大模型 × N 轮（每轮都慢）
异构：  大模型 × 1 轮（规划）+ 小模型 × N 轮（执行，每轮快 10–20 倍）
```

### 为什么不同

之前默认"一个模型打天下"。这个想法承认**智能需求是不均匀的**，按步骤的智能需求分配模型。类比：公司里架构师做设计（贵、慢、少），工程师照图施工（便宜、快、多）。

### 为什么之前没想到

1. 简单即美：一个模型、一个 API key、一套代码路径。
2. 小模型历史上太蠢，连"机械"步骤都做不好。但差距在缩小，速度差（10–20 倍）大到无法忽视。
3. 规划和执行的边界难划：哪一步需要判断力，事前不知道。

### 预期收益量级

- 假设大模型 TTFT 2000ms，小模型 TTFT 100ms（20 倍）。
- 3 轮任务：现在 = 3×2000 = 6000ms；异构 = 2000 + 2×100 = 2200ms（**−63%**）。
- 规划一次可复用（结合想法 1 的编译），摊销后更高。

### 最大风险

**小模型在"机械"步骤上翻车**。看着机械的步骤可能暗藏判断（"把文件写到合适的位置"里的"合适"需要上下文）。翻车后回退到大模型的延迟 + 重试成本可能吃掉收益。需要精确的"升级触发器"（小模型置信度低 → 转大模型）。

### 验证方法

1. T1–T6 用大模型做规划（输出步骤清单），小模型（用 sim-server 的 ultrafast profile 模拟 10 倍速）执行每步的 tool_call。
2. 对比异构 vs 全大模型的 wall time 和 success 率。
3. **可验证预测**：异构 wall < 全大模型的 60%，success 率差距 <5%；记录小模型触发升级的比例（预测 <15%）。

## 想法 5：推测执行（工具的分支预测）

### 核心思想

CPU 有分支预测：不等条件确定，先执行高概率分支，错了回滚。

Agent 能不能有**工具预测**？模型还没返回 tool_call，执行层根据任务 prompt 预测高概率工具调用，**先执行**。预测对了，省掉一整轮等待；错了，回滚（只对无副作用工具）。

```
现在：  prompt → 等 LLM (TTFT) → tool_call → 执行
推测：  prompt → [预测 write_file] → 先执行 ─┬─ 预测对：省掉等待
                                          └─ 预测错：回滚（仅只读工具）
```

### 为什么不同

之前所有想法都在"等 LLM"。这个想法**不等**。把串行的"LLM→工具"变成"预测执行"和"LLM 确认"并行。这是 CPU 设计师 40 年前学会的课：预测准确率够高时，推测执行永远赢。

### 为什么之前没想到

1. 感觉浪费：推测错了，白干活。但 CPU 也是这样，关键看准确率。
2. 副作用恐惧：工具会写文件、跑命令，推测错了怎么回滚？没人认真区分**只读工具**（read、list、search：推测零成本）和**写工具**（需要围栏）。
3. 预测器从哪来？任务 prompt → 工具调用的映射，需要数据。但 T1–T6 这类任务的模式高度重复，规则引擎就够。

### 预期收益量级

- 只读工具推测：准确率 >70% 时，省掉 70% 的只读工具等待轮次。
- T5（read-modify 任务）：read 是只读的，推测执行后 read 的 TTFT 等待消失。
- 组合 P1（确认轮消除）：推测 + 无确认轮，2 轮任务可能压到 1 轮以内。

### 最大风险

**写工具的推测灾难**。只读工具推测错了，最多浪费点时间；写工具推测错了，可能写错文件、删错东西。必须有铁律：**推测只用于只读工具**，写工具永远等 LLM 确认。这条铁律限制了收益上限，但保证了安全下限。

### 验证方法

1. 取 T1–T6 的任务 prompt，人工（或规则）预测第一轮的 tool_call。
2. 统计预测准确率（预测的工具 == 实际第一轮工具）。
3. **可验证预测**：Top-1 预测准确率 >70%；只读工具占比 >40% 的任务（如 T5），推测执行后 wall time −30%，零副作用事故。

## 总结：最值得试的 2 个

### 第 1 名：想法 1（编译式 Pipeline）

**为什么**：它是唯一**把 TTFT 干到 0** 的想法。其他想法都在"减少 TTFT"，这个想法"消灭 TTFT"。25 倍的预期收益是其他想法加起来都够不着的。而且它和用户已有的 agent-sock"烧录"概念天然契合——不是新方向，是已有方向的深化。

**切入点**：从 T1（创建文件）开始，任务模式最固定，编译模板最好写。验证成本最低（一人一天）。

### 第 2 名：想法 4（异构分解）

**为什么**：它是**现在就能用**的想法。不需要改架构，不需要新基础设施，只需要调两次 API（一次大模型，一次小模型）。63% 的预期收益，验证成本也是一人一天。而且它和想法 1 正交，可以叠加：大模型编译 pipeline，小模型执行变体。

**切入点**：用 sim-server 的 ultrafast profile 模拟小模型，零成本验证。先看 success 率差距，再决定是否引入真实小模型。

### 为什么不选其他

- 想法 2（常驻 agent）：收益大，但状态污染是根本性难题，验证周期长。等想法 1 验证完再说。
- 想法 3（批量）：收益真实，但只适用于批量场景（CI、自动化），交互场景用不上。受众窄。
- 想法 5（推测执行）：最酷，但收益上限被"只读工具"铁律锁死。不如先做想法 1，推测作为编译 pipeline 的加速器（编译时预取只读工具结果）。
